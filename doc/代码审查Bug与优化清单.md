- `待确认`：静态证据明确，但建议在目标浏览器/宿主中补充运行证据。

- `待修复` / `待优化`：问题或优化建议成立，尚未开始实施。
- `处理中`：已分配负责人并开始实施。
- `待验证`：代码已修改，等待按验收标准验证。
- `已关闭`：代码修改与验收均已完成；必须补充提交号或 PR、测试证据、关闭日期。
- `暂缓`：问题成立但当前版本不处理；必须记录暂缓原因和重新评估时间。

## 4. Bug 与风险项

### BUG-001 多实例仍由模块级单例和静态 LayerManager 驱动，无法保证数据隔离

- **类型 / 优先级 / 状态**：功能与架构缺陷 / P1 / 已确认（静态）
- **影响模块**：多实例、业务数据同步、视角命令、图层状态、资源巡检
- **代码位置**：`src/ui/MapView.tsx:200-217,263-280,294-315,328-343`；`src/render/LayerManager.ts:99-138`；`src/core/instance.ts:7-16`
- **问题与证据**：每个 `MapView` 虽登记进注册表，但 `LayerManager.map`、`mapInstance.current`、`layersReady.current` 仍是全局单值。`LayerSync` 不持有所属地图实例，所有数据更新都写到 `LayerManager` 当前指向的最后一个地图。任一实例卸载还会全局执行 `layersReady.current = false`、停止资源巡检并解绑瓦片降级。
- **影响**：A/B 两张地图同时存在时，A 的 props 更新可能写入 B；卸载 A 可能令 B 的 `isReady()` 变为 false，且关闭 B 仍需要的全局巡检。现有“多实例隔离已完成”的验收结论不充分。
- **建议方案**：建立 `MapRuntimeContext`，按 `instanceId` 保存 map、ready、LayerManager、DrawStore、控件、网格、主题和清理句柄；React 同步组件显式使用自身 runtime，命令式 API 通过实例 ID 路由。
- **验收标准**：同页创建 A/B，分别持续更新 props、MapDraw、主题、底图和网格；任一实例切换/卸载后另一实例的数据、相机、控件、事件、ready 状态和定时器均不变化。
- **预估工作量**：L

### BUG-002 卸载/重挂后事件和缩放重算失效，同时存在持续 RAF 泄漏

- **类型 / 优先级 / 状态**：生命周期缺陷 / P1 / 已确认（静态）
- **影响模块**：图元点击/悬停、扫描半径、目标聚合、标签分级、脉冲、FPS 统计
- **代码位置**：`src/primitives/api.ts:495-513`；`src/core/primitiveEvents.ts:103-137`；`src/render/LayerManager.ts:474-515`；`src/core/diagnostics.ts:120-149`；`src/ui/MapView.tsx:206-270`
- **问题与证据**：`zoomHooked` 和图元事件 `bound` 是一次性全局布尔值，`MapView` 卸载没有复位/解绑；新地图因此不会重新注册缩放或图元事件。与此同时 `LayerManager.stopPulse()`、`stopFpsCounter()` 未在卸载路径调用，RAF 可能在地图销毁后继续运行。
- **影响**：路由切页或 React StrictMode 重挂后，点击、悬停、聚合和标签缩放行为失效；后台存在无效 RAF，增加 CPU 占用并持有旧实例引用。
- **建议方案**：所有事件绑定返回真实 disposer；用 `WeakMap<Map, Cleanup[]>` 管理每实例监听器；卸载时调用 `off`、`cancelAnimationFrame` 并清空对应状态，避免全局布尔门闩。
- **验收标准**：连续挂载/卸载 20 次后监听器与 RAF 数量不增长；重挂地图后点击、hover、缩放重算均可用。
- **预估工作量**：M

### BUG-003 切换底图或精度后，手绘预览源和编辑手柄不会重建

- **类型 / 优先级 / 状态**：功能缺陷 / P1 / 已确认（静态）
- **影响模块**：手绘、量算、顶点编辑、底图切换、瓦片精度
- **代码位置**：`src/ui/DrawLayer.tsx:68-90,95-140`；`src/ui/MapView.tsx:294-313`
- **问题与证据**：`DrawLayer.setup()` 只在组件首次挂载时创建 `src-2d-interaction` 和四个预览图层。`map.setStyle()` 会清空全部自定义 source/layer，但样式恢复路径只重建 `LayerManager` 与网格，没有重新执行 `DrawLayer.setup()`。
- **影响**：切换底图/精度后，用户仍可触发交互事件，但预览线、面、吸附点和编辑手柄消失，编辑体验不可用。
- **建议方案**：让交互层监听 `style.load` 并幂等重建预览资源；或由统一的样式恢复编排器注册所有扩展层重建回调。
- **验收标准**：绘制中、编辑中和空闲状态分别切换底图/精度，预览和手柄均恢复，且监听器不重复。
- **预估工作量**：M

### BUG-004 首次落下线/面顶点时会提交非法单点 LineString

- **类型 / 优先级 / 状态**：GeoJSON 正确性缺陷 / P1 / 已确认（静态）
- **影响模块**：手绘折线、区域、测距、测面
- **代码位置**：`src/ui/DrawLayer.tsx:35-41,150-164,232-240`
- **问题与证据**：第一次单击后 `refresh()` 会执行 `line(pts)`；此时 `pts.length === 1`。GeoJSON `LineString` 至少需要两个位置，区域分支也会在只有一个点时生成单点 LineString。
- **影响**：MapLibre 可能拒绝 `setData`、控制台报错或不稳定显示，首次落点路径即会触发。
- **建议方案**：一个点时只画 vertex；两个及以上才创建 LineString；三个及以上才创建 Polygon。为预览 GeoJSON 增加结构断言测试。
- **验收标准**：五种绘制模式逐次落下 1/2/3 个点均无 MapLibre/GeoJSON 错误，预览按合法最小顶点数出现。
- **预估工作量**：S

### BUG-005 `setDrawKind()` 的设置在完成绘制时被忽略

- **类型 / 优先级 / 状态**：对外 API 行为缺陷 / P2 / 已确认（静态）
- **影响模块**：命令式绘制 API
- **代码位置**：`src/core/commands.ts:490-493`；`src/ui/DrawLayer.tsx:196-227`
- **问题与证据**：`finishDraw()` 计算了 `kind`，但点、面、线分支仍硬编码写入 `label`、`area`、`route`；除 ID 前缀外，调用 `setDrawKind()` 不会改变落库类型。
- **影响**：宿主按照公开 API 指定 `track` 等类型时得到错误的图元类别。
- **建议方案**：按绘制模式限制合法 `DrawKind`，并真正使用 kind 构造对应数据；不兼容组合在 `setDrawKind` 或完成时返回明确错误。
- **验收标准**：每个合法 mode/kind 组合落入预期 bag；非法组合有类型约束和运行时错误信息。
- **预估工作量**：S

### BUG-006 交互提示与实际行为不一致，编辑顶点时地图仍可同时平移

- **类型 / 优先级 / 状态**：交互缺陷 / P2 / 已确认（静态）
- **影响模块**：量算、顶点编辑、键盘操作
- **代码位置**：`src/core/interaction.ts:75-93`；`src/ui/DrawLayer.tsx:293-340,350-360,428-445`
- **问题与证据**：界面提示“Esc 清除”量算结果，但 `reset()` 不清空 `measurement`；按 Esc 后结果浮层仍存在。编辑模式进入 `else` 分支时调用 `map.dragPan.enable()`，拖动顶点可能同时拖动地图。输入框豁免检查发生在 Backspace/Delete 删除绘制点之后。

- **问题与证据**：虽然提供 `initialBasemapConfig()`，MapView 首次创建只对 `bootRef.current.config` 调 `buildStyle`，没有使用预注册的 current basemap。`setList/register` 将第一项设为 current 时也不广播。`BasemapDef.minZoom/maxZoom` 注释称“信息展示 + 约束”，`toConfig()` 却不应用它们。
- **影响**：宿主在渲染前注册底图不能保证首屏使用当前项；地图相机可进入底图未覆盖层级。
- **建议方案**：首次 buildStyle 使用 `initialBasemapConfig(config) ?? config`；明确 setList/register 的激活语义；合并并校验 basemap 的 min/maxZoom。
- **验收标准**：注册表当前项与 config 不同时，首帧直接加载当前项且不二次闪烁；相机与 source 层级约束符合定义。

### BUG-023 主题 tint 永远匹配不到模块自带 `base-tint` 图层

- **类型 / 优先级 / 状态**：主题功能缺陷 / P2 / 已确认（静态）
- **影响模块**：日间/夜间/高对比主题

- **影响**：三套主题声明的叠加色参数不生效，主题效果与文档/配置不一致。

- **预估工作量**：S

### BUG-024 新增图元类型未从唯一公开入口完整导出

### BUG-025 性能指标没有测量地图实际帧率，且声明的首屏预算从未参与回归

- **类型 / 优先级 / 状态**：可观测性缺陷 / P2 / 已确认（静态）
- **影响模块**：运行指标、性能基线、验收
- **代码位置**：`src/core/diagnostics.ts:120-149`；`src/core/perfBaseline.ts:48-71,224-267`
- **问题与证据**：FPS 计数器统计页面 `requestAnimationFrame` 回调，即使地图完全静止也接近显示器刷新率，不代表 MapLibre 实际渲染/交互帧率。`PerfBudget.firstInteractiveMs` 被定义但 `checkRegression()` 没有任何对应检查。
- **影响**：验收台可能报告“58/60 fps”而地图实际更新卡顿；首屏性能预算形同虚设。
- **建议方案**：结合 MapLibre render 事件与交互窗口测量有效帧；在 MapView 建图到 ready 之间埋点；区分静止刷新率、地图渲染帧率和长任务。
- **验收标准**：人为注入 100ms 主线程阻塞时指标能反映掉帧；首屏超 3s 时回归明确失败。
- **预估工作量**：M

### BUG-026 资源上限部分字段未生效，瓦片淘汰直接删除 MapLibre 私有结构

- **类型 / 优先级 / 状态**：资源管理缺陷 / P2 / 已确认（静态）
- **影响模块**：资源巡检、诊断、瓦片缓存
- **代码位置**：`src/core/resources.ts:16-31,54-91,99-143`；`src/core/diagnostics.ts:101-118`
- **问题与证据**：`maxErrors` 可配置但 diagnostics 硬编码只保留最先 50 条，`resourceUsage.errors` 永远返回 0。瓦片淘汰直接 `delete sourceCache._tiles[key]`，没有调用 MapLibre 的资源释放流程，且依赖不稳定的私有字段。上限值未校验，负数可导致全量淘汰。
- **影响**：资源报告错误，最新错误无法进入已满数组；瓦片缓存内部状态、GPU 资源或后续渲染可能不一致；非法配置可清空数据。
- **建议方案**：统一诊断 ring buffer 与 limits；校验所有限制为安全整数；优先使用公开缓存配置/API，不能安全逐块释放时不要直接改私有表。
- **验收标准**：maxErrors 动态生效并保留最新 N 条；usage 返回真实值；不同 MapLibre 小版本下压力测试无缓存异常和单调内存增长。
- **预估工作量**：M

### BUG-027 需求状态在 README、文档索引和验收台中互相矛盾

- **类型 / 优先级 / 状态**：项目文档缺陷 / P2 / 已确认（静态）

- **预估工作量**：S

## 5. 优化项

### OPT-001 建立直接针对生产源码的自动化测试与 CI 门禁

- **类型 / 优先级 / 状态**：质量工程 / P1 / 待优化

- **现状**：纯函数测试复制了一份算法实现，可能出现生产代码已变但副本仍通过的假阳性；`package.json` 没有 `test` 脚本，examples 也不参与 typecheck。本次执行该脚本为 17/17 通过，但不能证明生产模块同样通过。
- **建议方案**：使用 Vitest/Node 原生测试配合 TS loader，直接 import `src`；增加 `test`、`test:integration`、`typecheck:examples`、`lint`；CI 至少覆盖类型、单测、浏览器冒烟和构建。
- **验收标准**：修改生产算法会使对应测试失败；`npm test` 一条命令可运行；PR 必须通过全部门禁。
- **预估工作量**：M

### OPT-002 以实例 Runtime/Context 替代跨文件模块级可变状态

- **类型 / 优先级 / 状态**：架构优化 / P1 / 待优化
- **现状位置**：`src/core/instance.ts`、`src/core/store.ts`、`src/render/LayerManager.ts`、`src/primitives/api.ts`、`src/core/replay.ts`
- **现状**：地图、bags、主题、网格、降级、回放、监听器、定时器广泛使用模块级单例，导致多实例、SSR、热更新和测试隔离困难。
- **建议方案**：提供 `createMapRuntime(instanceId)`，内部持有 store、draw、layer、replay、diagnostics 和 disposer；默认 runtime 保持兼容，逐步给命令 API 增加实例参数。
- **验收标准**：不同 runtime 可并行测试且无需 reset 全局；模块导入不访问 window/document；默认单实例 API 保持兼容。
- **预估工作量**：L

### OPT-003 高频写入采用帧级合并和增量更新，避免每次 `add` 全量重建 GeoJSON

- **类型 / 优先级 / 状态**：性能优化 / P1 / 待优化
- **现状位置**：`src/primitives/api.ts:341-399,518-543,546-598`
- **现状**：非 batch 的每次 add/remove 都遍历该类全部 bag、重建 FeatureCollection 并 setData；所谓“单点更新”实际是 O(n) 全量提交。回放每帧还连续 set 多个种类。
- **建议方案**：默认在同一 animation frame 合并 dirty kind；提供同步 flush；对点位高频移动评估 feature-state、分片 source 或 worker 构建 GeoJSON；资源淘汰也使用 batch。
- **验收标准**：1万点下每秒 30/60 次单点更新仍满足帧预算；同帧多次写入每 kind 最多一次 setData。
- **预估工作量**：L

### OPT-004 样式重建改为可等待、可取消的统一事务

- **类型 / 优先级 / 状态**：可靠性优化 / P2 / 待优化
- **现状位置**：`src/ui/MapView.tsx:282-315`；`src/core/viewState.ts:92-151`
- **现状**：底图、精度、状态恢复都可能触发 setStyle，各子系统分散恢复；使用 `styledata` 一次事件或固定延时，连续切换时缺少 generation/cancel 控制。
- **建议方案**：建立 `rebuildStyle(reason)` 队列，以 generation ID 忽略过期回调；等待 `style.load` 后按固定顺序恢复 layer、draw、interaction、grid、theme、opacity、visibility。
- **验收标准**：连续快速切换 20 次后最终状态等于最后一次请求，无重复层、异常或旧回调覆盖。
- **预估工作量**：M

### OPT-005 输入校验统一为运行时 Schema，并建立坐标/样式边界

- **类型 / 优先级 / 状态**：健壮性优化 / P2 / 待优化

- **验收标准**：对所有公共数据类型都有合法/非法参数化测试，错误包含字段路径且不破坏现有合法数据。

### OPT-006 将 `preserveDrawingBuffer` 设为按需能力
